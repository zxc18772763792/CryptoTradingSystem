# AI 研究页面重设计方案

- 版本：v1.0
- 日期：2026-09-08
- 适用页面：`/` 中的「AI研究」页（`#ai-research`）
- 目标：让第一次使用的用户在 30 秒内知道“从哪里开始、现在进行到哪一步、下一步做什么”，同时保留现有研究、验证、注册和运行能力。

## 1. 设计结论

当前页面的问题不是功能不足，而是同一条链路被多个视觉模块重复描述：顶部有流程条和当前焦点，中部又有研究进度控制台，左栏同时放配置、Quick Path、研究任务、人工确认和数据诊断，中栏放候选，右栏再放注册；此外，页面存在 `0/1/2/3/4/5` 多套步骤编号。用户需要先理解系统内部对象（目标、思路、提案、任务、候选、注册），才能开始操作。

重设计采用一个明确的“研究任务”对象作为页面主线：

> **设定研究任务 → 生成方案 → 运行验证 → 选择候选 → 部署或归档**

页面只保留一条主 CTA 路径。自动研究是这条路径上的“快速模式”，不是第二套流程；实时信号、数据诊断、下单前复核和生命周期日志作为上下文或抽屉能力，默认不抢占主视线。

## 2. 现状审计

### 2.1 功能入口重复

| 现有入口 | 重复/混淆点 | 处理方式 |
|---|---|---|
| `0) AI判断市场并生成目标`、`1) 生成研究思路`、`2) 生成提案` | 用户必须理解内部生成顺序；目标可留空又造成“到底要不要填”的疑问 | 合并为“创建研究任务”，内部自动完成目标判断与方案生成；保留“编辑高级参数” |
| `⚡ one-click 自动研究+部署` | 与手动链路并列，且直接包含高风险部署 | 改为“快速运行”模式；默认只到纸面/影子运行，部署必须在候选详情中二次确认 |
| 顶部流程条、`当前研究进度`、左栏 Step、中心 Step、右栏 Step | 多套编号不一致，且同一状态在多个位置重复 | 只保留一个横向状态条 + 一个当前任务卡 |
| `研究任务`列表与候选列表 | 用户不清楚先选 proposal 还是 candidate | 采用“任务列表 → 任务结果”主从关系，并在列表中显示候选数/状态 |
| `研究数据诊断`、实时信号、研究候选运行信号 | 三个数据/信号区域职责边界弱 | 统一为“数据与运行状态”抽屉，按需展开 |
| `下单前 AI 复核` | 与研究流程关系弱，却占据主页面纵向空间 | 移到“安全与治理”抽屉，并显示当前生效范围摘要 |

### 2.2 信息架构问题

- 首屏同时回答“如何开始、系统状态、实时行情、历史候选、治理配置”五类问题，缺少优先级。
- 大量说明文字解释内部实现（例如 proposal、candidate、autonomous agent），不适合放在操作入口。
- 危险动作（注册、实盘候选、激活 live）与普通动作视觉权重接近。
- 空状态虽然给出文字提示，但没有把用户带到唯一可执行按钮。
- 操作结果、失败原因和下一步建议分散在通知、卡片和底部反馈区。

## 3. 新的信息架构

### 一级导航

保留产品层面的三个入口，避免把研究和执行混成一个页面：

1. **AI研究**：创建研究任务、验证候选、提交部署。
2. **AI自治代理**：实时盯盘和自动执行。
3. **研究工坊**：人工分析、因子、市场与跨资产研究。

在 AI研究页内不再使用“Step 1-2 / Step 3 / Step 4”作为栏目标题；步骤只在状态条中出现。

### AI研究页分区

1. **页头状态栏**：当前任务、数据就绪度、运行模式、更新时间。
2. **开始研究卡**：唯一主入口；默认只展示目标、标的、周期和“创建研究任务”。
3. **任务工作区**：左侧任务列表，右侧按状态展示结果。
4. **候选详情抽屉**：验证指标、风险、参数敏感性、部署选项和审计记录。
5. **辅助抽屉**：数据诊断、安全治理、历史记录。

## 4. 目标用户流程

### 4.1 新用户首次使用

1. 打开 AI研究页，看到空状态和一句话说明：“输入你想验证的交易想法，AI 会生成方案并回测。”
2. 填写研究目标（可留空）、币种、周期，点击 **创建研究任务**。
3. 系统自动完成市场判断、研究思路和提案生成；按钮进入 loading，页面显示单一进度状态。
4. 任务进入“待运行”，用户点击 **运行验证**，设置回测天数后提交。
5. 结果页按“推荐 / 可选 / 未通过”分组，默认选中推荐候选。
6. 用户查看风险摘要，选择 **纸面运行**、**影子运行** 或 **提交人工审批**。
7. 实盘激活永远需要单独确认、权限校验和风险闸门结果。

### 4.2 熟练用户快速运行

点击开始卡中的“快速运行”，使用上次配置和默认安全模式，一次提交“创建 + 验证”。完成后仍停在候选结果页；不会自动激活实盘。

### 4.3 研究失败或数据不足

页面在当前任务卡内显示“阻塞原因 → 处理按钮 → 重试”。例如数据不足时直接显示“资金费率缓存为空”，提供 **预热数据并重试**；不再让用户去多个模块寻找原因。

## 5. 页面线框与组件规格

### 5.1 页头状态栏

左侧：标题“AI研究”与副标题“从想法到可验证策略”。

中间：单一状态条：`设定任务 → 生成方案 → 验证候选 → 决定部署`。当前节点高亮，已完成节点可点击查看产物。

右侧：

- 数据状态：`就绪 / 部分缺失 / 过期`
- 运行模式：`Paper / Shadow / Live`
- `刷新`按钮

不在页头放实时行情列表和长说明。

### 5.2 开始研究卡（首屏主卡）

默认字段：

- 研究目标：多行输入，placeholder 给出一个可复制例子
- 标的：多选或逗号输入，默认 BTC/USDT、ETH/USDT
- 周期：多选，默认 5m、15m、1h
- 研究方式：仅显示“自动（推荐）”，高级模式中可切换模板/混合/开放草案

主操作区：

- 主按钮：**创建研究任务**
- 次按钮：**快速运行**（带“到候选结果为止”说明）
- 文本链接：**高级参数**

删除页面上的“0)”“1)”“2)”前缀；按钮文案用结果导向的动词。

### 5.3 任务列表

每一行只显示用户决策需要的信息：

- 任务名称（由目标生成，可编辑）
- 状态徽章：草稿、生成中、待验证、验证中、有候选、已部署、已归档
- 标的/周期
- 候选数量
- 最近更新时间

行内只保留 `打开`；删除、退出运行、归档放入“更多”菜单并二次确认。人工审批有独立警示徽章，但不单独占据一个大卡片。

### 5.4 结果工作区

顶部显示：`任务名称 · 验证区间 · 数据时间`，右侧提供 **运行验证**、**重新运行**。

候选列表采用表格/紧凑卡片混合布局：

- 第一列：推荐等级和策略名
- 核心指标：收益、Sharpe、最大回撤、交易次数
- 稳定性：样本外、参数敏感性、数据新鲜度
- 状态：待审批、纸面运行、影子运行、已拒绝
- 选择框：支持最多 3 个候选进行对比

默认排序按“风险调整后评分”，筛选收纳在工具栏，不再单独占用一整块说明区域。

### 5.5 候选详情抽屉

点击候选后从右侧打开，桌面端宽度 380–460px，移动端变为底部抽屉。结构固定为：

1. **结论**：推荐/谨慎/不建议 + 一句话原因。
2. **关键指标**：收益、Sharpe、回撤、胜率、交易数。
3. **风险与证据**：样本外表现、成本敏感性、参数稳定性、数据覆盖。
4. **运行选项**：纸面运行 / 影子运行 / 提交审批。
5. **实盘激活**：默认折叠；展示风险闸门、权限和人工审批状态后才可操作。
6. **生命周期**：生成、验证、注册、退出的时间线。

将当前 `ai-detail-panel`、候选对比弹窗和注册 Modal 统一为同一抽屉体系；对比最多 3 项，使用抽屉内的对比视图。

### 5.6 辅助抽屉

右上角“更多工具”打开三个折叠分组：

- **数据与信号**：新闻、宏观、funding、微观结构、研究候选运行信号。
- **安全与治理**：下单前 AI 复核、人工审批、权限和运行模式。
- **历史与诊断**：任务生命周期、失败详情、API/模型调用摘要。

这些内容默认不加载重型数据；打开分组时再请求，避免首屏同时触发多个接口。

## 6. 状态模型

前端统一使用以下任务状态，后端原始状态映射到展示状态：

| 展示状态 | 进入条件 | 用户下一步 |
|---|---|---|
| 草稿 | 只有配置尚未提交 | 创建研究任务 |
| 生成中 | 提案或思路任务运行 | 等待或取消 |
| 待验证 | 提案已生成无候选 | 运行验证 |
| 验证中 | 回测任务运行 | 查看进度 |
| 有候选 | 至少一个 validated 候选 | 选择候选 |
| 待审批 | 候选需要人工确认 | 审批/拒绝 |
| 运行中 | paper/shadow/live 状态 | 查看运行表现 |
| 已归档 | retired/退出 | 新建任务 |
| 阻塞 | 数据、权限或风险闸门失败 | 按原因修复并重试 |

前端只维护一个 `activeTaskId` 和一个 `activeCandidateId`。proposal/candidate 等内部 ID 仅在详情和诊断中显示。

## 7. 现有能力到新界面的映射

| 现有能力/接口 | 新入口 | 备注 |
|---|---|---|
| `/ai/proposals/generate`、`/ai/proposals` | 创建研究任务 | 合并目标判断、上下文和提案生成的前端编排 |
| `/ai/proposals/{id}/run` | 运行验证 | 统一回测天数、交易所配置 |
| `/ai/candidates`、`/ai/candidates/{id}` | 结果工作区/详情抽屉 | 保留现有数据结构，新增展示层映射 |
| `/ai/candidates/{id}/register`、`/promote` | 运行选项/实盘激活 | 高风险动作集中在详情抽屉 |
| `/ai/candidates/{id}/human-approve`、`human-reject` | 安全与治理 | 待审批徽章和抽屉内操作 |
| `/ai/oneclick/research-deploy` | 快速运行 | 默认不自动 live，部署拆成后续确认 |
| `/ai/diagnostics/funding-cache`、新闻接口 | 数据与信号 | 按需加载，失败在当前任务中提示 |
| `/ai/proposals/{id}/lifecycle`、候选 lifecycle | 历史与诊断 | 统一时间线组件 |

后端接口第一阶段不改名；通过前端 orchestration 层把多个请求组合成一个用户动作，并统一错误格式。

## 8. 交互与视觉规则

- 每个视口只允许一个主 CTA；“创建研究任务”是首屏唯一实心主按钮。
- 普通按钮使用“动作 + 结果”文案，例如“运行验证”“提交人工审批”。
- 危险动作使用橙/红色，并且必须显示影响范围、运行模式和审批状态。
- 所有异步动作显示三态：进行中、成功产物、失败原因；禁止只弹 toast 后消失。
- 空状态必须包含一个可执行按钮和示例输入。
- 解释性文字控制在两行内；详细说明放入 tooltip 或帮助抽屉。
- 颜色只表达状态：绿色通过/运行，黄色需要关注，红色阻塞/危险，灰色未开始。
- 桌面端采用 `minmax(280px, 320px) 1fr` 的任务列表 + 结果区；详情用抽屉而不是固定第三列。
- 1024px 以下改为单列：任务列表、结果、详情依次显示；顶部状态条可横向滚动。
- 所有状态徽章提供文字，不依赖颜色；按钮和输入控件支持键盘焦点及 aria-label。

## 9. 实施拆分

### Phase 0：埋点与兼容层（0.5 天）

- 建立展示状态映射和 `activeTaskId/activeCandidateId` 单一状态源。
- 保留现有 DOM id 和 API 调用，增加 orchestration 函数，避免一次性改后端。
- 记录创建、快速运行、验证、候选选择、部署确认的事件。

### Phase 1：首屏和主流程（1–2 天）

- 重写 `#ai-research` 首屏结构，移除重复流程条、flow console 和长说明。
- 合并目标判断/思路/提案为“创建研究任务”。
- 将 one-click 改名为“快速运行”，默认到候选结果。
- 增加统一进度、阻塞原因和下一步 CTA。

### Phase 2：任务与候选工作区（1–2 天）

- 任务列表与候选结果建立明确主从关系。
- 候选卡片改为可排序表格，详情、对比和注册统一为抽屉。
- 统一清理、退出、归档入口，补齐确认和权限反馈。

### Phase 3：辅助能力收纳（1 天）

- 数据诊断、实时信号、安全治理、生命周期改为按需抽屉。
- AI自治代理页只保留研究候选只读摘要，去除重复控制项。
- 异步请求改为按需加载并显示局部错误。

### Phase 4：验证与发布（0.5–1 天）

- 桌面 1440/1920、平板 1024、移动 390 三档截图验收。
- 验证新用户路径、已有 proposal/candidate 回填、取消/重试、权限拒绝和数据缺失。
- 运行现有 AI research API/UI 测试，补充状态映射、主 CTA 和高风险二次确认测试。
- 更新 `web/asset_versions.py`，避免旧 CSS/JS 缓存。

## 10. 验收标准

### 可用性

- 新用户无需阅读帮助文字即可完成“创建任务 → 运行验证”。
- 页面任何时刻只有一个明确的下一步按钮。
- 用户能在 3 秒内找到当前任务、状态、阻塞原因和下一步。

### 一致性

- 页面不再出现 `0) / 1) / 2) / Step 1-2 / Step 3 / Step 4` 混用。
- proposal、candidate、自治代理的内部术语不出现在主操作文案中。
- 快速运行、手动创建和候选部署使用同一状态条与反馈组件。

### 安全

- 快速运行不会绕过人工审批或风险闸门直接进入 live。
- live 激活前必须显示模式、仓位、风险闸门和审批状态，并要求二次确认。
- 权限/API 失败在当前上下文可见，不能只显示“请求失败”。

### 性能

- 首屏只请求任务、摘要和必要状态；数据诊断与信号接口延迟到抽屉打开。
- 切换任务时取消过期的候选详情请求，避免旧结果覆盖新任务。
- 1920px 无横向滚动，详情抽屉打开后主内容仍可读。

## 11. 暂不纳入本轮

- 不修改研究算法、评分公式、候选生命周期和交易执行逻辑。
- 不把 AI自治代理并入研究流程；两者保持不同权限和风险边界。
- 不删除后端旧接口；待新 UI 稳定后再评估接口收敛。

## 12. 建议的第一批代码文件

- `web/templates/index.html`：替换 `#ai-research` 结构，保留必要兼容 id。
- `web/static/js/ai_research.js`：新增任务编排、状态映射、统一反馈与抽屉控制。
- `web/static/js/ai_research_runtime.js`：改为按需加载数据/信号摘要。
- `web/static/js/ai_research_diagnostics.js`：合并数据诊断和治理摘要。
- `web/static/css/style.css`：新增 `#ai-research` scoped layout，逐步停用旧三栏规则。
- `web/asset_versions.py`：同步 CSS/JS 版本。
- `tests/web/`：增加主流程、状态映射、高风险确认和响应式结构测试。

这份方案以现有接口和数据模型为约束，先解决用户路径和信息层级，再逐步清理实现层重复，适合分阶段上线和回滚。

## 13. 自主多轮迭代研究（必须保留并前置）

你提到的“自主多轮迭代研究”是 AI研究页的核心差异化能力，不能被归类为普通的“快速运行”。它应当是创建研究任务时可选择的研究模式，并拥有自己的进度、预算和停止条件。

### 13.1 当前实现事实

仓库中已有 `core/ai/autonomous_research_loop.py`，具备以下能力：

- 持久化配置和轮次记录到 `autonomous_loop.json`。
- 按间隔自动触发研究轮次，默认间隔 3600 秒。
- 每日轮次上限 `1–24`，默认 6 轮。
- 支持最多 8 个标的、最多 3 个周期（15m/1h/4h）。
- 每轮检查历史数据是否存在、是否过期、是否至少有 100 根 K 线。
- 将最近候选和最近轮次反馈交给 LLM，生成新的可证伪假设和策略变更。
- 通过 fingerprint 避免重复研究程序。
- 每轮受最大回测次数限制（8–80），只排队有限回测。
- 明确禁止自动部署：当前作用域是“LLM 假设 → 有界回测 → 候选反馈”。

后端已有 `GET/PATCH /api/ai/research-loop`。目前前端只在运行模式信息中以一行文字和“启用/暂停研究循环”按钮呈现（`ai_research.js` 的 operating-mode banner），用户很难发现，也看不到轮次详情、预算消耗和停止原因。

### 13.2 新的研究模式选择

在“开始研究卡”顶部增加模式选择，使用三个互斥选项：

| 模式 | 适用场景 | 结果 |
|---|---|---|
| **单轮验证** | 已有明确想法，快速验证 | 生成一个任务并运行一次回测 |
| **自主迭代**（推荐探索） | 希望 AI 根据结果持续改进 | 在当前任务下运行 N 轮，持续产生候选和反馈 |
| **定时研究** | 允许系统每天自动探索 | 按计划运行，达到每日预算自动暂停 |

“自主迭代”和“定时研究”共用同一研究任务与候选池；区别是前者由用户启动并有总轮次/总预算，后者由调度器按时间间隔运行并有每日预算。不要再把它们藏在“高级参数”或 operating-mode banner 中。

### 13.3 自主迭代配置面板

选择“自主迭代”后展开配置，默认值应安全且易懂：

- 最大迭代轮数：3（范围 1–12）
- 每轮最大回测：24（范围 8–80）
- 总回测预算：80（按实际运行数扣减）
- 研究间隔：立即连续 / 每轮等待数据刷新
- 探索强度：保守 / 平衡 / 激进（映射现有 `exploration_bias`）
- 停止条件：达到目标评分、连续两轮无改进、预算耗尽、数据过期
- 标的和周期：复用开始卡配置

“定时研究”额外显示：运行间隔、每日最大轮数、启用时间窗和暂停日期。所有预算字段都显示“预计消耗”，避免用户误以为一次点击只产生一个回测。

主按钮根据模式动态变更：

- 单轮验证：**创建并运行验证**
- 自主迭代：**启动自主迭代**
- 定时研究：**保存计划并启用**

### 13.4 迭代运行面板

任务进入自主迭代后，结果工作区顶部切换为“迭代驾驶舱”，固定显示：

- 总进度：`第 2 / 6 轮`
- 预算：`已用 31 / 80 次回测`
- 当前状态：生成假设、验证中、等待数据、已收敛、预算暂停、失败
- 当前假设：一句话显示本轮要验证什么
- 本轮变化：相对上一轮修改了哪些策略/参数
- 本轮结果：最佳候选评分、Sharpe、回撤、是否超过上一轮
- 下一步：继续、等待、停止的明确原因

下方使用时间线而非多张重复卡片：

`第 1 轮 基线 → 第 2 轮 改进 → 第 3 轮 淘汰 → 第 4 轮 当前`

每个轮次可展开查看假设、输入反馈、生成草案、回测结果和淘汰原因；默认只展开当前轮次。

### 13.5 用户控制

驾驶舱只保留三个控制：

- **暂停迭代**：保留状态和预算，当前回测完成后暂停。
- **立即停止**：停止后不再自动排队新轮次，已产出候选保留。
- **继续下一轮**：仅在暂停、等待或失败可恢复时出现。

不要提供“自动部署”按钮。任何候选进入纸面、影子或 live，都必须回到候选详情抽屉执行现有审批和风险闸门。

### 13.6 收敛与反馈规则

每轮结束后前端应展示机器可读的停止原因：

- `目标达成`：候选评分和风险约束均达到用户目标。
- `连续无改进`：连续两轮最佳评分提升低于阈值。
- `预算耗尽`：达到轮次或回测上限。
- `数据阻塞`：历史数据不足或过期。
- `重复假设`：fingerprint 命中，等待下一次新假设。
- `系统失败`：LLM、回测或队列异常，可重试。

“无改进”不能只显示红色失败；要显示上一最佳值、本轮最佳值和阈值，让用户知道为什么停止。

### 13.7 与单轮研究的界面关系

单轮和自主迭代共用任务列表、候选表格和候选详情抽屉。差异只出现在：

- 任务状态增加“迭代中 / 已收敛 / 已暂停”。
- 结果区增加迭代驾驶舱和轮次时间线。
- 候选显示 `G0/G1/G2` 代际标识，并支持“查看上一代”。
- 任务列表显示“当前轮次、预算、最近改进”。

这样用户只需学习一套任务和候选概念，不会出现“普通研究页”和“自主研究页”两套系统。

### 13.8 后端/前端落地建议

第一阶段复用现有 `GET/PATCH /ai/research-loop` 与 `rounds` 数据，不改变研究算法。建议补充：

- `POST /api/ai/research-loop/run-now`：用户明确启动一次迭代，返回 round id。
- `POST /api/ai/research-loop/pause`、`/resume`、`/stop`：语义化控制，避免前端通过 PATCH 猜测状态。
- `GET /api/ai/research-loop/{task_id}/timeline`：返回任务级轮次、候选代际和停止原因。
- 状态 payload 增加 `current_round`、`max_rounds`、`backtests_used`、`backtests_budget`、`best_score_before/after`、`stop_reason`、`next_run_at`。

若暂时不扩展 API，前端也应先把现有 `rounds`、`attempts_today`、`config`、`status` 变成可见的迭代驾驶舱，并在轮次请求期间轮询 `/ai/research-loop`，而不是只显示一个启用开关。

### 13.9 自主迭代验收标准

- 用户从 AI研究首屏能发现并开启“自主迭代”，无需进入运行模式或高级诊断。
- 运行中可看到当前轮次、假设、预算消耗、最佳结果和下一步。
- 暂停、停止、恢复后状态与预算不丢失；刷新页面可恢复驾驶舱。
- 每轮都有明确的改进/淘汰原因，重复 fingerprint 不会生成重复任务。
- 自主迭代永远不会绕过候选详情中的审批和风险闸门进入 live。
- 迭代完成后，用户能直接从最后一轮跳转到最佳候选详情。


> **概念边界**：`research_search_loop.py` 的搜索循环是单个提案内部的参数/模板搜索；`autonomous_research_loop.py` 的自主研究循环是跨轮次、利用历史候选反馈重新生成假设的持久化调度。新 UI 将两者分别标记为“单轮内部搜索”和“自主迭代轮次”，避免再次混淆。
